# M12 0.2

Milestone Timing: Mirrors `M12` in [Project plan](../PLAN.md): start `2026-10-09` (begins when `M11` ends), target end `2026-11-06` (four-week window, shifted on `2026-08-06` with the extended `0.1.2` window and the resequenced `M11` outreach milestone).

Status: Drafted, not yet started.

## Desired Outcome

TermiWeb should leave `M12` with a real `0.2` release whose scope stays bounded but is not artificially limited to one feature. The QR connect affordance is already included as the first committed feature candidate, and the milestone should still allow additional `0.2` feature candidates to join if they fit the timing and verification bar.

## 1. Work Breakdown

1. [ ] Lock the `0.2` feature set before implementation gets too far ahead.
   1. [ ] Treat the QR connect affordance as already included in `M12`, not as the definition of the milestone.
   2. [ ] Decide which additional bounded `0.2` feature candidates, if any, join `M12` alongside QR.
   3. [ ] Draft or update any focused specs needed for the additional included features before implementing them, and pause for user review where rule `1.16` applies.
   4. [ ] Re-summarize [the product spec](../PRODUCT_SPEC.md) only if the approved focused specs change a durable product invariant or direction.

2. [ ] Ship the QR connect affordance inside `0.2`.
   1. [ ] Draft a focused QR connect spec under `docs/specs/` covering when the affordance appears, what URL it encodes, how localhost/LAN/WAN addresses are treated, error or fallback states, and any desktop/mobile presentation details.
   2. [ ] Pause for user review of the QR draft spec before implementation (rule `1.16`).
   3. [ ] Decide whether the client can derive the shareable address directly from `window.location` or needs a server-provided canonical access address when reverse proxies or custom hosts are in play; record the choice in this worklist or the focused spec before coding.
   4. [ ] Implement the chosen address-selection path so non-loopback sessions produce a stable URL for QR generation while loopback sessions do not advertise a misleading cross-device target.
   5. [ ] Add tests for any new address-normalization or visibility helper that gates the QR affordance.
   6. [ ] Add the top-bar affordance and QR presentation so it is obvious but clearly secondary to normal terminal use.
   7. [ ] Keep the affordance hidden on loopback and usable on both workstation and phone-sized browsers when the current session is reachable from another device.
   8. [ ] Preserve the existing host-identity and version visibility after the new control lands.

3. [ ] Ship any additional included `0.2` features behind QR.
   1. [ ] Add the implementation and verification tasks for each additional included feature here or in tightly linked focused specs or supporting worklists once those features are approved for `M12`.
   2. [ ] Keep the added scope small enough that `0.2` can still pass the local release gate honestly inside the current milestone window.

4. [ ] Verify the `0.2` scope and ship the release surface.
   1. [ ] Verify the QR path from a second device on the same LAN, including scan-to-login and attach to an existing live instance.
   2. [ ] Verify localhost behavior on the host device so the QR affordance stays absent and no misleading address is shown.
   3. [ ] Verify each additional included `0.2` feature against its approved scope before closing the milestone.
   4. [ ] Run the local release gate: `npm run typecheck`, `npm test`, `npm run build`, `npm run build:site`, `npm run package:release`.
   5. [ ] Update release notes, `package.json` / `package-lock.json`, the website download surface, README release wording, and any packaged-install copy that becomes stale once `0.2` lands.

## 2. Verification Checklist

1. [ ] The QR affordance appears only when the current access address is not loopback.
2. [ ] The encoded URL opens the real TermiWeb login or workspace on a second device without depending on manual hostname editing.
3. [ ] The localhost path stays uncluttered and does not imply that `127.0.0.1` is useful from another device.
4. [ ] Any additional included `0.2` features ship against approved scope instead of expanding informally mid-milestone.
5. [ ] The `0.2` local release gate passes and the release surface accurately describes the shipped scope.
6. [ ] Existing desktop and mobile terminal flows still work: login, instance select, paste, modifier controls, selection or copy, and reconnect.
